# Штаб Офлайн — план безопасного подключения к Google Sheets

Версия прототипа: `PWA-OFFLINE-0.1-pre`. Это не установленная версия CRM.

## Уже реализовано

- Отдельная статическая PWA (можно открыть с HTTPS и установить на главный экран iPhone).
- `Service Worker` кэширует только локальную оболочку, без сетевых зависимостей.
- `IndexedDB` содержит `cases`, `events`, `queue`, `meta`.
- Редактирование задачи, планового и юридического сроков, а также результата заседания и даты следующего события — одна атомарная IndexedDB-транзакция.
- Для каждого локального действия создаётся `opId`; в записи содержатся `caseId`, `baseVersion`, изменения, `eventId` и `expectedEventVersion`. Локальные изменения не отмечаются как отправленные.
- Демонстрационные данные — вымышленные; нет входа в рабочую CRM.

## Следующий шаг: отдельный тестовый контур

1. На основе **актуальных полных серверных исходников** создать отдельный тестовый Apps Script проект с копией CRM, не меняя рабочие листы и действующий `/exec`.
2. Обеспечить проверенную авторизацию устройства/пользователя; не использовать API-ключ/токен в общедоступном JS. GitHub Pages допустим только для клиентского кода без секретов.
3. Реализовать защищённый серверный API для получения снимка с `serverRevision`, списком изменений и безопасной отправки операций. Для внешнего PWA нужен специально предусмотренный HTTPS-шлюз с корректным CORS и проверкой учётных данных; простой вызов `google.script.run` вне iframe Apps Script не работает.
4. Сервер сохраняет `opId` в журнал подтверждений и при повторной отправке возвращает тот же результат без повторного начисления XP, записи истории или создания заседаний.
5. Сервер сравнивает ревизию дела и события с ожидаемой: при конфликте **не перезаписывать данные**, а возвращать актуальное состояние и список конфликтных полей.
6. Сначала получать снимок, затем отправлять очередь в порядке создания; подтверждать операции по одной с обязательным чтением успешного ответа, оставлять неподтверждённые локально.
7. Если результат запроса неоднозначен (тайм-аут после отправки), повторять **тот же `opId`** и проверять серверный журнал, а не генерировать новое действие.
8. Серверная логика дат/CASE ID/EVENT ID/XP остаётся единственной: обе версии UI используют одинаковые валидаторы и методы ядра.
9. Для выданного устройства: управляемый вход/выход, шифрование чувствительного локального кэша, удаление кэша, минимизация полей, ограничение времени автономной работы с актуальными данными, резервное восстановление несинхронизированной очереди.

## Особые ограничения iPhone

Синхронизацию при закрытом приложении нельзя считать гарантированной. Запуск отправки при открытии приложения, переходе в активное состояние и при успешном восстановлении связи, с видимым счётчиком неподтверждённых действий.

## Нельзя делать

- Подключать демонстрацию напрямую к рабочей CRM без отдельного разрешения и серверного тестирования.
- Хранить длинноживущие секреты или доступ к Google Sheets в публичных статических файлах.
- Перезаписывать дела по принципу «последняя запись побеждает».
- Убирать запись из очереди до серверного подтверждения.
- Считать локальное сохранение успешной записью в Google Sheets.
